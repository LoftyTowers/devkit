# Testing strategy

## Scope

Governs mechanically enforceable constraints on Angular unit tests, component tests, service tests, HTTP tests, route tests, reactive-form tests, and coverage gates across the workspace.

## Rules

- Every component, service, pipe, directive, and guard generated by `ng generate` MUST have a co-located `.spec.ts` file.
  **Verification mechanism:** CI script / file-system check — glob match `src/**/*.ts` against `src/**/*.spec.ts`; fail on unmatched non-spec files.

- The workspace test builder MUST be set to `@angular/build:unit-test` in `angular.json`.
  **Verification mechanism:** Config validation — CI script inspects `angular.json` `architect.test.builder` equals `@angular/build:unit-test`.

- `TestBed.configureTestingModule()` MUST NOT be called after `TestBed.createComponent()` within the same spec.
  **Verification mechanism:** Custom ESLint rule or CI grep — detect `configureTestingModule` calls appearing lexically after `createComponent` in the same `describe`/`beforeEach` block.

- `provideHttpClient()` MUST be provided BEFORE `provideHttpClientTesting()` in the `TestBed` providers array.
  **Verification mechanism:** Custom ESLint rule — AST check ordering of provider calls within `configureTestingModule`.

- Every test suite that uses `HttpTestingController` MUST call `httpTesting.verify()` in an `afterEach` block.
  **Verification mechanism:** Custom ESLint rule — detect `HttpTestingController` injection without a corresponding `verify()` call in `afterEach`.

- Coverage thresholds MUST be configured in `angular.json` under `coverageThresholds` with explicit numeric values for `statements`, `branches`, `functions`, and `lines`.
  **Verification mechanism:** Config validation — CI script reads `angular.json` and asserts `coverageThresholds` object exists with all four keys set.

- `ng test --coverage` MUST pass in CI without falling below configured thresholds.
  **Verification mechanism:** CI script — `ng test --no-watch --coverage` exit code must be 0.

- Route tests MUST use `provideRouter()` with a real route configuration; the Angular `Router` MUST NOT be replaced with a mock.
  **Verification mechanism:** Custom ESLint rule — detect `{ provide: Router, useValue: ... }` or `{ provide: Router, useClass: ... }` in test providers and report as error.

## Prohibited patterns

- MUST NOT import from `v2.angular.io` or reference `AngularJS`-era testing APIs.
  **Verification mechanism:** ESLint `no-restricted-imports` — ban imports matching AngularJS module paths.

- MUST NOT use `HttpClientTestingModule` (the NgModule-based API); use `provideHttpClientTesting()` instead.
  **Verification mechanism:** ESLint `no-restricted-imports` — ban `HttpClientTestingModule` from `@angular/common/http/testing`.

- MUST NOT use the deprecated `RouterTestingModule`; use `provideRouter()` with `RouterTestingHarness`.
  **Verification mechanism:** ESLint `no-restricted-imports` — ban `RouterTestingModule` from `@angular/router/testing`.

## Allowed deviations

- MAY use `NO_ERRORS_SCHEMA` for shallow component tests when the sole purpose is testing the component under test in isolation from nested component trees.

- MAY use `vi.useFakeTimers()` / `vi.useRealTimers()` (Vitest native fake timers) as a replacement for Zone.js-based timer helpers.
